# 日迹 · 个人生活记录助手 — 设计方案 v0.1

> 一句话定位：**一个统一的记录引擎 + 若干可插拔的记录模块**，用来把生活里值得留痕的事（钱、身体、输入）记成一条时间线。

📍 阶段：设计完成 + M1 骨架已实现（可编译运行）

---

## 一、先说结论：为什么不按「记账小程序 + 加几个功能」来做

你列的需求是「记账、运动、体重、阅读、喝酒」，看起来像 5 个功能。但它们的**数据结构是同一个东西**：

| 场景 | 记什么 | 共同结构 |
|---|---|---|
| 记账 | 金额、分类、支付方式 | 时间 + 若干字段 + 一个主数值 |
| 运动 | 项目、时长、距离 | 时间 + 若干字段 + 一个主数值 |
| 体重 | 体重、体脂 | 时间 + 若干字段 + 一个主数值 |
| 阅读 | 书名、时长、页数 | 时间 + 若干字段 + 一个主数值 |
| 喝酒 | 酒种、毫升、状态 | 时间 + 若干字段 + 一个主数值 |

三条路线对比：

| 方案 | 做法 | 结果 |
|---|---|---|
| A. 拼装式 | 记账一套表、运动一套表、体重一套表 | 每加一个模块要改 **4 处**：数据表、录入表单、列表渲染、统计口径。第 5 个模块时必然重构 |
| **B. 注册表引擎（本方案）** | 一份记录结构 + 一份类型配置 | 新增模块 = **加 20 行配置**，页面/统计/图表全自动适配 |
| C. 纯自由 JSON | 什么都能记，字段随便填 | 没有统一口径，统计做不出来，最后退化成备忘录 |

选 B。代价是需要一层抽象（约 200 行服务代码），收益是**这个产品未来三年加任何新模块都不用动页面**。

## 二、核心设计：类型注册表（Type Registry）

### 2.1 两种记录形态

理解这一点，后面所有设计都顺：

- **事件型（event）**：一件事发生一次，一天可以多条，统计口径是**求和 + 次数**
  → 支出、收入、运动、喝酒、阅读
- **指标型（metric）**：一天一个状态值，统计口径是**取最新值 + 变化量**
  → 体重、睡眠

如果混在一起处理，体重会被"求和"成 700kg——这是这类 App 最常见的翻车点。

### 2.2 配置结构

```js
{
  key: 'weight',                    // 唯一标识，存进记录里
  name: '体重', icon: '⚖️',
  color: '#8B5CF6', soft: 'rgba(...)',  // 主题色 + 浅底色
  kind: 'metric',                   // event | metric
  primary: {                        // 主数值：趋势图与汇总都取它
    field: 'weight',                // 对应 fields 里的 key
    agg: 'last',                    // sum | last
    fmt: 'kg',                      // 格式化器：money|duration|kg|hours|ml|count
    chartBase: 'auto'               // 柱状图基线：auto 表示从最小值起算（体重必需）
  },
  fields: [                         // 动态表单，页面按此渲染
    { key:'weight', label:'体重', type:'decimal', unit:'kg', required:true },
    { key:'bodyFat', label:'体脂率', type:'decimal', unit:'%' }
  ],
  titleField: '',                   // 列表主标题取哪个字段
  subFields: ['bodyFat']            // 列表副标题取哪些字段
}
```

字段支持的 `type`：`money` / `number` / `decimal` / `picker` / `text`。
**新增字段类型只需在 `record/index.wxml` 加一个分支**，现有类型零改动。

### 2.3 新增一个「喝茶」模块，需要改什么

只改 `config/recordTypes.js`，加一段：

```js
{
  key: 'tea',
  name: '喝茶',
  icon: '🍵',
  color: '#8C6239',
  soft: 'rgba(140, 98, 57, 0.10)',
  kind: 'event',
  primary: { field: 'ml', agg: 'sum', fmt: 'ml' },
  fields: [
    { key: 'kind', label: '茶种', type: 'picker', options: ['绿茶','红茶','乌龙','普洱'], default: '绿茶' },
    { key: 'ml', label: '茶水量', type: 'number', unit: 'ml', required: true, placeholder: '300' }
  ],
  titleField: 'kind',
  subFields: []
}
```

保存后：首页自动出现「喝茶」卡片、录入页自动出现茶种选择器、统计页自动多一个 tab、列表筛选自动多一项。
**页面代码 0 行改动。** 这就是为什么这个架构值得。

## 三、信息架构与页面清单

```
Tab 1 今日 ──── 看板（6 个模块数字）+ 最近记录 + 悬浮记一笔
Tab 2 记录 ──── 按月分组的流水，支持类型筛选 / 改月份
Tab 3 统计 ──── 单模块趋势柱图 + 构成分布
Tab 4 我的 ──── 预算、模块开关、导出、清空、隐私说明
                └─ 记一笔 / 编辑页（非 tab，从任意入口进入）
```

| 页面 | 路径 | 作用 | 关键交互 |
|---|---|---|---|
| 今日 | `pages/home/index` | 今天的全貌 | 模块卡片点一下直接进入该类型录入；显示本月支出与预算进度 |
| 记录 | `pages/list/index` | 流水查询 | 月份切换、类型筛选、按日分组、长按编辑/删除 |
| 统计 | `pages/stats/index` | 单维度分析 | 切类型、切 7/30 天、柱状趋势、分类占比 |
| 我的 | `pages/mine/index` | 配置与数据 | 预算、模块开关、导出 JSON、清空 |
| 记一笔 | `pages/record/index` | 录入 / 编辑 | **同一份 schema 动态渲染表单**，切换类型即时换表单 |

主包体积：全部页面 + 代码约 120KB 源码，距 2MB 上限极远，**M1 不需要分包**。
`lazyCodeLoading: requiredComponents` 已开，按需注入组件。

## 四、数据模型

### 4.1 记录结构（统一，与类型无关）

```js
{
  id: 'r_mg2k1a_x9f2',      // 本地唯一 ID（时间戳36进制 + 随机）
  type: 'expense',           // 关联 recordTypes 的 key
  date: '2026-10-19',        // 归属日期，统计按此聚合（字符串，避免时区坑）
  time: '12:30',
  value: 38.5,               // 从 fields[primary.field] 抽出的主数值，null 表示无数值
  fields: {                  // 类型专属字段，schema 由 recordTypes 定义
    amount: 38.5, category: '餐饮', pay: '微信', note: '外卖'
  },
  note: '',
  deleted: false,            // 软删除，便于 M2 云同步做增量
  createdAt: 1760000000000,
  updatedAt: 1760000000000
}
```

**为什么把 `value` 冗余出来**：统计和图表只读 `value`，不用每次按类型去 `fields` 里找主字段。这就是"统一记录模型"的关键——**类型差异在写入时被归一化，读取端只面对一种结构**。

### 4.2 本地存储

| Key | 内容 | 说明 |
|---|---|---|
| `life_log_records_v1` | 记录数组 | 单 key 上限 10MB，约 5 万条以内无压力 |
| `life_log_settings_v1` | 配置对象 | 启用模块、月预算、云同步开关 |

超过 **3000 条**建议开云同步（M2），因为 `wx.getStorageSync` 全量反序列化开始有感知延迟。

### 4.3 D2 云开发迁移对照（M2 已落地）

| 本地 | 云开发 |
|---|---|
| `life_log_records_v1` 数组 | 集合 `records`，一条记录一个 doc（`_id` = 记录 `id`） |
| `services/record.js` 内部读写 | 仍是本地写；写后由 `services/sync.js` 调云函数 `records` 增量上行 |
| `life_log_settings_v1` | 暂不上云（换机后重填环境 ID 即可恢复同步） |
| 无索引 | `records` 建复合索引 `openid`（升序）+ `updatedAt`（升序），增量拉取走这条查询 |

服务层对外签名（`add/update/remove/query/series`）保持不变，页面代码不用动——这是分层的意义。

### 4.4 云同步协议（v0.2.0）

```
客户端 → 云函数 records：{ action:'sync', pushes:[...], lastSyncAt:Number }
云函数 → 客户端：       { code:0, serverTime:Number, pushed:Number, pulls:[...] }
```

四条关键设计：

1. **双水位线**：拉取水位线用**服务器时间**（`lastSyncAt`），推送水位线用**客户端时间**（`lastPushAt`）。若两条合并成一条，手机时钟比服务器慢时，新记录会因 `updatedAt < 水位线` 被永久跳过，永远推不上去。
2. **Upsert 天然去重**：云函数用记录 `id` 作 `_id` 写库，刚推上去的记录在回声拉取里被合并回本地不会产生重复。
3. **冲突 last-write-wins**：单用户多设备场景，以 `updatedAt` 大者胜；本地有尚未推送的更新时保留本地版本（按顺序"先推后拉"即可保证）。
4. **客户端不直连数据库**：全部读写走云函数 + 字段白名单，避免权限配错导致越权读到他人数据。

## 五、关键交互设计

### 5.1 三秒记一笔（核心体验）

痛点不是"能不能记"，是"愿不愿意记"。所以：

1. 首页模块卡片**点一下直接进对应类型的录入页**，不是先进"选择类型"再选分类
2. 表单只有 **1~2 个必填字段**（支出：金额必填，分类有默认值；体重：只要体重）
3. 日期默认今天、时间默认当前，**不填也能存**
4. 保存后立即返回，首页 onShow 自动刷新

实测路径：打开小程序 → 点「支出」→ 输金额 → 保存，**4 次点击**。

### 5.2 首页看板

六张卡片，每张回答一个问题：

- 支出：今天花了多少 / 今天几笔
- 体重：最近一次多少 / 比上次 ↑↓ 多少（这是最想看的数字）
- 运动：今天动了多久 / 几条
- 其余同理

指标型卡片的副标题是**变化量**不是条数——因为体重的信息量在"变了多少"，不在"记了几次"。

### 5.3 统计

- 事件型：合计 / 日均 / 次数 / 有记录天数
- 指标型：平均 / 最高 / 最低 / 记录天数
- 柱状图：纯 WXSS 实现，**不引入 ECharts**（ECharts 小程序版压缩后 ~500KB，为一个趋势图不值得）
- 分布：取该类型第一个 picker 字段做维度（支出=分类、喝酒=酒种、运动=项目）

## 六、技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | 微信原生 | 单人应用，不需要跨端；原生调试链路最短、包最小 |
| 存储 | 本地 Storage 优先 | 零成本、零备案、离线可用、无隐私上传风险 |
| 后端 | 云开发（**M2 已接入**，默认关闭） | 免服务器免备案，个人主体可开通；M1 不接是为了先验证"你愿不愿意记"；M2 接了但默认关闭，本地仍是唯一工作副本 |
| 图表 | 纯 WXSS | 省 500KB 包体 |
| tabBar | 文字版（4 项） | iconPath 非必填，先跑通再加图标 |

**为什么 M1 不上云**：记账类 App 的死亡原因从来不是"没同步"，是"记了三天不记了"。先用最轻的方式验证习惯，再为习惯付云开发的成本。

## 八、合规前置（提审前必看）

> 以下为设计阶段的预判，**微信平台规则会更新，最终以官方最新文档为准**。

| 项 | 结论 | 依据 / 官方文档 |
|---|---|---|
| 类目 | 「工具 - 效率 / 记录」类，个人主体可申请，无需额外资质 | [类目资质](https://developers.weixin.qq.com/miniprogram/product/material/category.html) |
| 健康数据（体重/睡眠） | 可以做**记录与展示**，但**不得输出医疗建议、诊断结论、健康风险评分**（如"你的体重已达肥胖标准""建议就医"）。一旦提供健康判断，可能被要求医疗类资质 | [运营规范](https://developers.weixin.qq.com/miniprogram/product/reject.html) |
| 饮酒记录 | 只能做个人记录。**不得出现酒类商品推荐、购买链接、品牌推广**——酒类销售属特殊类目，需资质 | 同上 |
| 记账功能 | 纯个人记账工具（记录 + 统计）不涉及支付牌照。**不要做**：多人共同账户、资金归集、代收代付、借贷撮合、分账结算——这些会触及金融类目 | 同上 |
| 隐私 | M1 不收集任何个人信息（无手机号、无位置、无通讯录），数据不出本机。M2 若加手机号登录 + 云同步，**必须**配置《用户隐私保护指引》并在调用前弹窗授权 | [隐私接口](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/privacy.html) |
| 诱导分享 | 分享入口不做"分享才能看数据/得奖励" | 运营规范 |

本项目 M1 **不调用任何隐私接口**（无 `getLocation` / `getUserProfile` / `getPhoneNumber`），`app.json` 里 `requiredPrivateInfos` 为空，这是提审最省事的形态。
